# Лабораторная работа №4 — SAGA Choreography: Публикация поста с модерацией

Проект представляет собой микросервисную архитектуру блог-платформы, реализованную на **FastAPI** с использованием **Celery + Redis** для асинхронной обработки задач и **SAGA Choreography** для распределённой публикации статей с модерацией.

В этой лабораторной работе реализован бизнес-процесс публикации поста с автоматической модерацией, генерацией превью, публикацией и отправкой push-уведомлений подписчикам. Всё взаимодействие между шагами происходит через очередь задач без центрального оркестратора.

Проект состоит из нескольких независимых сервисов и воркеров, запущенных в Docker Compose.

## Архитектура проекта

### Структура папок
```
backend/                  # Основной сервис постов (FastAPI)
users_service/            # Сервис пользователей и подписок (FastAPI)
notifications_worker/     # Воркер отправки push-уведомлений
moderation_worker/        # Воркер модерации
preview_worker/           # Воркер генерации превью
publish_worker/           # Воркер финальной публикации
dlq_worker/               # Воркер обработки Dead Letter Queue (компенсации)
nginx/                    # API Gateway
docker-compose.yaml       # Оркестрация всех сервисов
```

### Ключевые технологии:
- **FastAPI** — API-сервисы
- **SQLAlchemy + AsyncPG** — работа с PostgreSQL
- **Celery + Redis** — асинхронные задачи и очередь
- **JWT** — аутентификация пользователей
- **Внутренние API-ключи** — service-to-service аутентификация
- **SAGA Choreography** — распределённый процесс публикации
- **DLQ** — обработка ошибок с компенсациями

### Механизмы аутентификации:
1.  **JWT (End-user Auth):** Для доступа пользователей к публичным эндпоинтам через заголовок `Authorization: Bearer <token>`.
2.  **S2S (Service-to-Service API Keys):** Для взаимодействия между воркерами и внутренними эндпоинтами через заголовок `Authorization: Token <key>`. Доступ разграничен по областям (Scopes): `moderate`, `preview`, `publish`, `profile`.

## Жизненный цикл поста

Поле `status` в таблице `articles` управляет состоянием статьи:

| Статус | Тип | Описание |
| :--- | :--- | :--- |
| `DRAFT` | Начальный | Исходное состояние созданной статьи. |
| `PENDING_PUBLISH` | Переходный | Статья находится на этапе обработки (модерация/превью). |
| `PUBLISHED` | Финальный (Успех) | Статья доступна для чтения, все этапы саги завершены. |
| `REJECTED` | Финальный (Отказ) | Модерация отклонила контент. |
| `ERROR` | Финальный (Сбой) | Возникла неустранимая техническая ошибка при обработке. |

Переходы между статусами происходят только в результате локальных транзакций в сервисе постов.

## Описание бизнес-процесса (SAGA)

Процесс публикации инициируется пользователем через запрос `POST /articles/{slug}/publish`.

1.  **Этап модерации (`post.moderate`):**
    *   Воркер выполняет проверку контента.
    *   **Успех:** Генерация события `post.generate_preview`.
    *   **Отказ:** Вызов компенсирующего эндпоинта `/reject` (статус → `REJECTED`).
2.  **Генерация превью (`post.generate_preview`):**
    *   Воркер создает изображение/миниатюру статьи.
    *   Вызов внутреннего эндпоинта `/preview` для сохранения URL.
    *   Генерация события `post.publish`.
3.  **Финализация публикации (`post.publish`):**
    *   Content Service переводит статью из `PENDING_PUBLISH` в `PUBLISHED`.
    *   Генерация события `post.notify`.
4.  **Уведомление подписчиков (`post.notify`):**
    *   Воркер запрашивает список подписчиков автора и отправляет push-уведомления.

## Обработка исключений и надежность

Все задачи в очереди настроены на автоматический повтор при возникновении временных ошибок (например, недоступность сети или смежного сервиса):
*   **Количество попыток:** 3.
*   **Стратегия:** Экспоненциальная задержка (Exponential Backoff).

При исчерпании лимита попыток задача перемещается в очередь `dlq`. Обработчик `dlq_worker` анализирует тип задачи и выполняет соответствующую компенсацию:
*   Сбой модерации → перевод в `REJECTED`.
*   Сбой превью или публикации → перевод в `ERROR`.
*   Сбой уведомлений → только логирование (публикация считается завершенной).

Все операции идемпотентны и проверяют текущее состояние объекта перед внесением изменений.

## Руководство по запуску проекта для демонстрации

### 1. Развертывание
```bash
# 1. Подготовка окружения
cp .env.example .env

# 2. Сборка и запуск
docker compose up -d --build

# 3. Применение миграций (выполняется автоматически при старте)
```
### 2. Настройка межсервисной авторизации

Для корректной работы воркеров необходимо сгенерировать API-ключи:
1.  Авторизоваться в Swagger под учетной записью администратора.
2.  Использовать эндпоинт `POST /internal/api-keys` для создания ключей.
3.  Разместить полученные токены в конфигурационных файлах (или переменных окружения) соответствующих воркеров.


### 3. Мониторинг

Отслеживание состояния распределенных задач осуществляется через логи контейнеров:
*   `docker logs -f backend` — транзакции и API запросы.
*   `docker logs -f {name}_worker` — выполнение этапов саги и обработка DLQ.

Интерфейс Swagger доступен по адресу: `http://localhost/docs`.
